# طاولة التداول المؤسسية — Institutional Trading Desk

نظام وكلاء متعدد الأدوار يحاكي **طاولة تداول مؤسسية** حقيقية: فصل صلاحيات صارم
(Front / Middle / Back Office)، بوابتا جودة إلزاميتان (مخاطر ثم التزام)، أحجام صفقات
بمعادلات ظاهرة، سجل صفقات ورقي، ولجنة مراجعة أسبوعية تغلق حلقة التحسن.

> ⚠️ **إخلاء مسؤولية:** هذا النظام تعليمي — ينتج تحليلًا وخططًا لمحفظة **ورقية** فقط.
> ليس نصيحة استثمارية، ولا ينفذ أوامر حقيقية، ولا يدير أموالًا.

## خط الجلسة اليومية (9 مراحل، بوابتان)

| المرحلة | الملف | الوكيل | عناصر البوابة الإلزامية |
|---|---|---|---|
| طلب الجلسة | `00_request.md` | — | `# طلب` + الأصول + الحدود |
| جمع البيانات | `01_data.md` | t02 | روابط http + مصدر لكل رقم |
| التحليل (توازٍ) | `02a/02b/02c/02d_*.md` | t03–t06 | ماكرو: سيولة · فني: دعم/مقاومة/**إبطال** · تدفقات: تموضع/معنويات · كمي: تقلب/ارتباط/VaR |
| **بوابة المخاطر (1)** | `03_risk.md` | t07 | **إخلاء مسؤولية + سيناريو + وقف + احتمال** (مجموع 100%) |
| مخصص المراكز | `04_sizing.md` | t08 | حجم المركز بمعادلة ظاهرة + وقف + نسب R |
| **بوابة الالتزام (2)** | `05_compliance.md` | t09 | إخلاء مسؤولية + فحص الحدود + سطر `قرار:` |

وضع المراجعة الأسبوعية (`--mode review`): طلب ← جمع السجلات ← مقاييس الأداء
(معدل الربح، متوسط R، التراجع، الانضباط) ← لجنة المخاطر والالتزام ← تقرير الدروس.

## الحدود المؤسسية المضمّنة (لا تُتجاوز مهما كانت «الفرصة»)

| الحد | القيمة | يفرضه |
|---|---|---|
| مخاطرة الصفقة | ≤ 1% من رأس المال (سقف مطلق 2%) | t08 |
| ميزانية المخاطرة الكلية (Portfolio Heat) | ≤ 5% | t07 + t09 |
| الرافعة | ≤ 2× وبمبرر مكتوب فقط | t08 + t09 |
| التعرض المترابط (BTC+ETH كتلة واحدة) | ≤ 40% | t08 |
| مسافة الوقف | ≥ 1×ATR (لا وقف داخل الضجيج) | t07 بمرجع t06 |
| Kill-Switch | خسارة يومية 3% / أسبوعية 6% → إيقاف | t07 |
| كيلي | المخاطرة ≤ ¼ Kelly | t08 |

## آلية التنسيق
- **توازٍ مقصود:** المحللون الأربعة لا يرون عمل بعضهم → استقلالية الآراء ثم الدمج عند المخاطر.
- **فصل صلاحيات ثلاثي:** من يحلل لا يحدد الحجم، من يحدد الحجم لا ينفذ، وكلمة المخاطر فوق الجميع.
- **بوابات آلية:** المحرك يرفض أي ملف ينقصه عنصر إلزامي — لا التفاف على المراجعة.
- **أثر تدقيق:** كل قرار تمرير/إرجاع موثق في `status.json`، وكل صفقة في السجل تحيل مرجعها.
- **حلقة التحسن:** سجل كل جلسة يغذي لجنة المراجعة الأسبوعية (جودة القرار ≠ نتيجته).

## التشغيل

```bash
# وضع الطيار المساعد: المحرك يفرض البوابات ويطبع برومبت كل وكيل،
# والوكلاء (أو إنسان) يكتبون الملفات في مجلد المهمة:
python3 trading_orchestrator.py jobs/desk_2026-09-12

# التشغيل الكامل عبر LLM (يتطلب LLM_API_KEY — راجع .env.example):
python3 trading_orchestrator.py jobs/desk_2026-09-12 --api

# جلسة يومية جديدة بتاريخ اليوم (ينشئ الطلب من القالب):
python3 daily_desk.py            # أو: --manual للطيار المساعد

# لجنة المراجعة الأسبوعية:
python3 daily_desk.py --mode review
```

**سير العمل في وضع الطيار:** شغّل ← المحرك يطبع المطلوب ← أنتج الملفات (يدويًا أو
بوكلائك) ← أعد التشغيل ← البوابة تتحقق وتنتقل للمرحلة التالية أو ترفض مع ذكر الناقص.

## مثال مرجعي كامل
`jobs/desk_2026-09-12/` — جلسة كاملة من الطلب حتى السجل (BTC/ETH/الذهب) ببيانات
مرجعية بتاريخ 11 سبتمبر 2026 ومصادرها، لتوثيق مستوى الإخراج المطلوب من كل وكيل.

## التوسعة
- **أصل جديد:** يُضاف لقائمة الأصول في الطلب — لا تغيير في الوكلاء (الجميع متعدد الأصول أصلًا).
- **وكيل جديد:** أسقط بطاقة في `agents/` + مرحلة في `PHASES_*` داخل `trading_orchestrator.py`.
  أمثلة جاهزة للإضافة: وكيل أخبار آنية (RSS)، وكيل خيارات (تحليل Vol Surface)،
  وكيل تنويع عبر أسهم/مؤشرات.
- **حدود مختلفة:** تعدَّل في قالب الطلب `briefs/template_request_daily.md` — البوابات تقرؤها من هناك.
